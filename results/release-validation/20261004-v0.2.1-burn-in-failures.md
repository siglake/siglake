## The 24-hour timeout was the first audit checkpoint poll

The last workload cohort completed at 05:29:59.713. The duration loop then
ended. The marker query
`SELECT 1 AS audit_probe /* release-validation-audit-llvalidate-db1a5ad129fc */`
completed with HTTP 200 at 05:30:09.850. The next operation was the first
`await_audit_checkpoint` persistence probe:

```sql
SELECT count(*) AS n
FROM query_audit
WHERE query = 'SELECT 1 AS audit_probe /* release-validation-audit-llvalidate-db1a5ad129fc */'
```

The query server began planning and scanning that request at 05:30:26, but the
runner's 30-second HTTP request expired at 05:30:39.881. No
`query_audit_checkpoint` event or end-of-run component restart followed. This
was a harness control-flow defect: the checkpoint had a 120-second poll deadline,
but one transport timeout escaped instead of consuming part of that deadline.
It does not prove the marked audit row was absent. The runner now retries a
transport timeout within the same 120-second bound and still propagates an HTTP
error or a wrong persistence/coverage answer.

The event-table cohort, total, grouped and filtered oracles preceding this
operation passed. Those checks do not substitute for the unfinished audit-row
persistence and inline-aggregate assertions, so the attempt remains failed.

## The 72-hour missing cohort was host capacity exhaustion

Both runs started on the same Docker backing filesystem with about 202.4 GB
available. They had separate Compose projects and volumes, but those volumes
shared that filesystem. Immediately before the 24-hour cleanup it had 35.5 GB
available. Cleanup released about 82 GB, raising available capacity to
117.4 GB. The remaining 72-hour run fell to 4.68 GB available by 18:41:52.

At 18:43:01 MinIO refused an events-table metadata write with HTTP 507
`XMinioStorageFull`; subsequent data-file, metadata and audit writes received
the same response. The next 100-event cohort remained at zero committed IDs for
its 120-second deadline. The runner correctly classified this as Docker
backing-store exhaustion. The evidence directories themselves occupy about
355 MB combined, so retained metrics and logs did not account for the roughly
198 GB 72-hour volume at hour 37.

The 72-hour volume consumed about 113 GB between the 24-hour cleanup and hour
37. A linear continuation would put it near 500 GB at 72 hours, before allowance
for changing rewrite amplification. The rerun recipe therefore uses one run at
a time, at least 256 GiB available for 24 hours or 640 GiB for 72 hours, and a
64 GiB monitored reserve. Crossing the reserve is an infrastructure failure;
it does not relax the final row or audit assertions.

## Conditional guard refusals

The 24-hour log contains 70 side-aggregate conditional guard refusals: 32 in
the 02:37 restart window, six in the 03:37 window and 32 in the 04:38 window.
The 72-hour log contains 86: 70 after the 16:41 query-server restart and 16
after the 17:41 restart. All came from the query server while publishing
`siglake.query_audit`; the compactor did not emit this refusal. A process that
already cached a successful conditional-write verdict continued normally.
A restarted query server had an empty verdict cell, retried the live warehouse
probe on each five-second audit flush, and eventually cached a success.

This establishes a restart-triggered, transient failure of the query server's
cold conditional-write probe. It does not establish whether MinIO returned an
unrecognized precondition response, a transport error or another S3 error. The
v0.2.1 log recorded only the outer `cannot establish warehouse
conditional-write compatibility` context. The same refusal occurred in the
earlier short public-image smoke with ample capacity, so storage pressure alone
does not explain it.

Current 0.3.0 source logs the complete probe error chain and its release harness
fails artifact review on any refusal. It still uses the same production probe
and has no retained supported-store run proving the refusal gone. The diagnostic
change makes the next occurrence classifiable; it is not evidence of a product
repair. The fail-closed guard, retry-on-next-flush behavior and exact aggregate
coverage assertion remain unchanged.
