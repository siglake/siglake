# Siglake soak-test corpus

A reusable, deterministic dataset + query suite for AWS soak testing.

## What it is

Three artifacts, materialized into a single directory:

| File                   | What it carries                                                |
|------------------------|---------------------------------------------------------------|
| `events.ndjson`        | One deterministic source JSON object per line; `load` converts it to OTLP/HTTP JSON and posts it to `/v1/logs`. |
| `queries.json`         | An array of `{id, description, sql, spl, expected}` — `verify` executes only `sql`; the unused `spl` member remains for artifact compatibility. Every entry has a closed-form expected result computed during generation. <!-- vendor-name-ok: artifact compatibility, see #4601 --> |
| `manifest.json`        | `{seed, events, start_time, window_hours, distribution_version}`. Carries everything needed to regenerate `events.ndjson` byte-for-byte. |

The pair `(seed, events, start_time, window_hours)` is the corpus's content address. Same inputs → same `events.ndjson` bytes → same `queries.json` expecteds.

## Why a corpus (vs. random loadgen)?

`siglake-loadgen` (bench mode) is good for "drive the ingester at N events/sec for D seconds and report tail latency." It is **not** good for "verify the query layer returns the right answer over a known dataset" — its events are random per run with no ground-truth oracle.

The corpus is the verification dataset:

- Every event is generated by a pure function `event_for(index, seed, start_time, window_secs)`. Same input → same byte-for-byte event.
- Aggregates (count by sourcetype, status=500 count, etc.) are computed as the events are written, so the **expected** value in `queries.json` is exactly what running the SQL form should return.
- The artifact directory is `tar`-friendly: generate once, upload to S3, reuse forever.

## Sizes

There's no fixed list of canonical sizes — you pass `--events`. Rules of thumb:

| Tier   | `--events`   | `events.ndjson` size | Generate time on a laptop |
|--------|--------------|---------------------|---------------------------|
| smoke  | 10_000       | ~2.5 MB             | <1s                       |
| small  | 1_000_000    | ~250 MB             | ~10s                      |
| medium | 10_000_000   | ~2.5 GB             | ~2 min                    |
| large  | 100_000_000  | ~25 GB              | ~20 min                   |

`events.ndjson` is uncompressed; the file streams nicely with `aws s3 cp` and gzips to ~25% (lots of repeated tokens).

## Workflow

### 1. Generate once

```bash
cargo run --release -p siglake-loadgen --bin siglake-corpus -- \
  generate \
  --out ~/corpus/medium \
  --seed 42 \
  --events 10000000
```

Default `--start-time 2026-01-01T00:00:00Z`, default `--window-hours 24`. Override to span a longer window if you want `WHERE timestamp BETWEEN ...` queries that hit multiple Iceberg `day(timestamp)` partitions.

The artifact is fully self-contained. Stash it anywhere:

```bash
# tar + gzip; ~25% of raw size
tar -cz -f corpus-medium.tar.gz -C ~/corpus medium

# or push the dir to S3 and re-pull on the soak host
aws s3 cp --recursive ~/corpus/medium s3://my-soak-artifacts/corpus-medium/
```

### 2. Load into a running Siglake

```bash
cargo run --release -p siglake-loadgen --bin siglake-corpus -- \
  load \
  --corpus ~/corpus/medium \
  --target http://localhost:8088 \
  --tenant default \
  --batch-size 500 \
  --concurrency 8
```

`load` streams `events.ndjson` line-by-line, converts each event to an OTLP log
record, and POSTs JSON batches to `/v1/logs` at the configured concurrency. Add
`--token <bearer-token>` when ingest authentication is enabled. The exit status
only reflects load success — query verification comes next.

For an AWS-shaped soak, port-forward (or hit the LoadBalancer) and run the same command against the public ingester endpoint.

### 3. Verify

After the load finishes (and you've given the compactor time to commit a snapshot — typically a few seconds with default thresholds), run:

```bash
cargo run --release -p siglake-loadgen --bin siglake-corpus -- \
  verify \
  --corpus ~/corpus/medium \
  --query-target http://localhost:8089 \
  --token "$SIGLAKE_QUERY_TOKEN"
```

This iterates `queries.json`, runs each entry's `sql` against the query-server, and compares the response to `expected`. Exit 0 on full match, non-zero with a diff on any mismatch. Sample output:

```
  ok  total_count — Total event count.
  ok  nginx_count — Count of nginx:access events.
  ok  status_500_count — Count of HTTP 500 nginx events (the 1% bin in the shape).
  ok  auth_failure_count — Count of failed auth events.
  ok  count_by_sourcetype — GROUP BY sourcetype (alphabetical).
  ok  count_by_host — GROUP BY host (alphabetical, 16 rows).

all 6 queries match expected.
```

## Distribution shape

Three sourcetypes, fixed mix:

| sourcetype     | weight | shape                                                                |
|----------------|-------:|----------------------------------------------------------------------|
| `nginx:access` |    60% | classic nginx access log line; HTTP method/path/status/response_ms   |
| `app:api`      |    35% | JSON-ish API log: endpoint/latency_ms/user_id                        |
| `auth:syslog`  |     5% | login/logout/sudo + success=true/false + user_id                     |

`nginx:access` status codes are drawn from `{200, 304, 400, 404, 500, 503}` with 200 dominant (~92%) and 500 rare (~1%). The `status_500_count` query is the canary that the rare-bucket arithmetic survived the round-trip.

Hosts cycle through a fixed pool of 16 (`web-0[1-8]`, `api-0[1-4]`, `auth-0[1-4]`); `count by host` returns exactly 16 rows for any non-trivial dataset.

Timestamps are uniform over `[start_time, start_time + window_hours)`. Iceberg's `day(timestamp)` partition spec naturally cuts the data into per-day partitions, which is what time-range queries lean on.

The exact bins live in `siglake_loadgen::corpus::DISTRIBUTION_VERSION` (currently `1`). If a shape ever changes, that constant bumps and old `queries.json` files refuse to verify against a freshly-generated corpus — the manifest carries the version explicitly so the mismatch is loud.

## Reproducibility

`generate_is_byte_for_byte_reproducible` (unit test) checks that the same `(seed, events, start, window)` produces identical `events.ndjson` bytes across runs. This is the property the artifact relies on: stash the file once, regenerate later if you lose it, get the same bytes back. The same property means you can ship `queries.json` separately from `events.ndjson` and they'll still match.

## Where to put the artifact in S3

For a customer-shared soak corpus we use the `s3://<bucket>/soak/<size>/` convention:

```
s3://<your-corpus-bucket>/medium/
├── events.ndjson         (2.5 GB)
├── manifest.json
└── queries.json
```

Permissions: artifacts are non-sensitive (no real customer data) so a public-read prefix works, but the production pattern is per-account IAM. The `load` and `verify` subcommands talk only to your Siglake deployment — they don't touch S3 directly; you pre-pull the corpus to local disk first.

## Backpressure baseline (Phase 4.13)

The 4.12.14/4.12.16 mpsc-fed writer queue returns `503 Service Unavailable` + `Retry-After` when a tenant's lane is full. A one-shot curl flood doesn't surface this in a chart-default deployment — `wal_max_events=4096` means the writer drains a batch in milliseconds and the bounded mpsc never stays full. Sustained EPS at-or-above-write-throughput is what makes the 503s show up.

`siglake-loadgen` now histograms HTTP status codes — `200` / `429` (rate limit) / `503` (backpressure) — so you can run a baseline against any deployment and read the split directly.

```bash
# Bring up a deployment with tight WAL thresholds + small backpressure
# capacity so the bound is reachable at modest load:
helm upgrade --install siglake deploy/helm/siglake \
  --set ingester.walSegmentMaxEvents=1 \
  --set ingester.walSegmentMaxAgeSecs=60 \
  --set ingester.backpressure.capacity=4 \
  --set ...

# Steady-state flood: 5k EPS for 30s across 8 workers.
kubectl -n siglake port-forward svc/siglake-ingester 8088:8088 &
cargo run --release -p siglake-loadgen -- \
  --target http://localhost:8088 \
  --eps 5000 --duration 30s \
  --workers 8 --batch-size 50
```

The final summary surfaces:

```
==== siglake-loadgen summary ====
  elapsed:        30.02s
  events sent:    63450
  achieved EPS:   2113
  bytes sent:     19567200
  HTTP 2xx:       1269
  HTTP 429:       0       (rate limit)
  HTTP 503:       1731    (backpressure)
  HTTP other:     0
  errors:         0 (transport+other)
  latency (us):   p50=… p95=… p99=…
```

What to look for:

- **2xx + 503 ≈ total requests** with `errors == 0` confirms backpressure is doing its job (rejecting at the entry point instead of stalling).
- **503/total ratio** is the throttle aggressiveness. >50% means the deployment is under-provisioned for the target EPS — scale ingesters or raise `backpressure.capacity`.
- **429s** appear only when `ingester.rateLimit.ratePerSec > 0`. If they show up unexpectedly, the rate limiter is squeezing legitimate traffic.

A deployment with `backpressure.capacity=0` (default) will surface backpressure as **errors** instead — the request queues behind `Mutex<WalWriter>` until the reqwest 10s timeout fires. That's the signal to flip on the backpressure path.
